# Property editor layout

This rule applies to the application's object views, supporting dialogs, Settings and dashboard editors. Preserve the current fonts, colors, native editor behavior, DLMS bindings and Gurux.DLMS package.

## Standard property sections

- Use an upper-left aligned property region with a maximum width of **800 logical pixels at 96 DPI**. Do not stretch simple settings across a large monitor.
- Use one **144 logical-pixel label column**, including the label-to-field gap. It may shrink to **100** in narrow containers. Wrap long labels and measure their height rather than cutting them off or moving individual inputs to unrelated columns.
- Align peer input left and right edges. The field or field-plus-action group has a **640 logical-pixel maximum**. The region reserves up to 16 pixels at its right edge. On smaller windows, use the available space; these are maximums, not minimum window sizes.
- Keep standard object rows on the existing 40-pixel rhythm: 32-pixel scalar input surfaces with 4-pixel vertical insets. Hosted comboboxes match adjacent text-box height by sizing the native closed selection field; preserve the font, dropdown item height, arrow and single native frame. Reapply after font/DPI/handle changes without resizing an already-correct control. Compact native controls and dialog rows retain their native preferred heights and measured margins.
- Related scalar sections on the same visible page share absolute label and input edges, including at narrow widths. Presentation-only nested groups use headings in one property grid; retain the original bound controls and their handlers. Action Schedule and Parameter Monitor use the shared property/list layout, with the expanding list and actions below their scalar sections.
- Keep groups that own enabled/visible state intact. Remove redundant horizontal indentation and use `EditorLayoutPolicy.ShareLabelColumn(nestedRows, commonRootRows)` for related property sections. Bind directly to the common root table so narrow-window caption measurement is shared; copying a fixed width or only removing padding does not establish alignment.
- Put captions above full-width lists. For deliberately paired data editors, top-align captions beside lists, trees, multiline text and alternate structured editors; do not vertically center them beside a tall surface. Scalar captions remain vertically centered. Long native checkbox captions need a full-width row or measured wrapping; do not truncate them inside a narrow label column.
- Register, Extended Register and Demand Register use `CompactActions` for their native method buttons: align the first action with the field column, use 32-logical-pixel minimum button height and a 40-pixel normal row, remove default child insets, and measure any wrapping. Preserve each original GXButton, method index, state and confirmation behavior.
- Register Activation list actions meet the right edge of their list. Use the shared 32-logical-pixel action group with 4-pixel vertical insets and an 8-pixel gap between Masks actions. Clear legacy anchors while retaining the original buttons, method indices, active-mask binding and native state.
- Schedule groups Enable/Disable, Insert and Remove at the Entries list right edge, in that visual and tab order. Retain the original GXButtons and method indices, using a shared content-safe width with a 128-logical-pixel minimum, 32-pixel height, 8-pixel peer gaps and 4-pixel vertical insets. Keep the Entries list height, columns and bindings intact.
- Labels and controls remain in reading/tab order. Keep the original bound instances and handlers when moving them into a layout table.
- Implement standard rows through `EditorLayoutPolicy.ConfigurePropertyTable`. Use `ConstrainSection` only for explicitly compound property regions. Recompute sizes from constants and the current `DeviceDpi`; never multiply previously scaled values or fonts.

## Button groups

- Size and place each button according to its workflow. Object actions and custom application actions use a **32-logical-pixel** minimum height; native modal confirmations retain the **28-pixel** native dialog style. Keep existing fonts, colors, rounded/native rendering, original instances, handlers, method indices and enabled/visible states.
- Use `ActionButtonPanel` with `ButtonLayoutPolicy.Apply` for pure action groups. Peer buttons have an **8-pixel gap**, no outside horizontal button margins, and **4-pixel first/last vertical insets** in object list/method rows. A single object row is normally 40 pixels high; reserve measured height when it wraps. Native dialog action bars retain their named content-edge/vertical insets.
- Measure complete captions through both WinForms native layout (context-free text measurement) and the current control drawing context; reserve the larger width plus native border, existing padding and a small text reserve. Use a shared content-safe width within a peer group. Width is suited to content rather than one fixed width for every command. Schedule retains a 128-pixel minimum; ordinary object groups normally start at 100, native confirmations at 80. Recompute from constants and both measurement paths after font, handle and DPI changes; never scale a previous font or measured width.
- Align list actions with the actual right border of the list they operate on. Direct list/footer pairs have a 4-pixel list-to-button gap; do not keep a second bottom margin on the list. Tab page/frame insets count when locating nested lists. Association Short Name's object commands belong inside Objects; IPv6 retains one shared footer for its three address tabs and aligns it to the active nested list.
- Preserve semantic placement: Register-family method actions start on the property field rail; inline field actions stay beside their editor; Profile Generic keeps the requested top-right Reset/Capture stack. Association Logical Name keeps its leading local Edit command separate from trailing remote Add/Remove. Separate unrelated remote methods from list editing.
- Confirmation groups in an AutoSize table column use `wrap: false` so the column reserves the full intrinsic width of OK/Cancel. Let bounded content rows wrap; do not let an auto-width slot turn a horizontal confirmation pair into a clipped vertical stack.
- Native left-to-right flow determines wrapped reading order, then each completed row is aligned to its intended edge. Add/Edit/Remove must remain in that visual and keyboard order across rows. Never reverse the whole sequence to achieve right alignment. Keep all wrapped rows reachable; clear obsolete designer anchors before handing positioning to the layout group.
- `ButtonLayoutPolicy.ApplyToButton` measures an inline native action without taking over its parent's placement. Related inline action rows use `MatchInlineWidths` so their measured button widths and adjacent input edges agree; retain each caption's required width rather than forcing a smaller fixed size. Mixed checkbox/action rows retain their controls and order while footer buttons use the same native height. Native toolbar items, small icon/browse/accessory buttons and OS-owned dialogs retain their native roles; name those exceptions in the button coverage ledger.
- Check all compiled object, supporting-dialog and application surfaces. Record buttonless screens, intentionally hidden controls and vendor/native exceptions explicitly. Compare rendered borders and actual outer HWND/parent coordinates, not a client origin plus an outer size. Verify every fixed-footer action through all ancestor clips; an AutoScroll flag alone does not make an off-screen footer reachable. Exercise normal, intermediate, narrow and restored sizes, conditional tabs, actual 96/120-DPI moves and minimize/maximize. Use disposable fixtures; do not trigger meter/service commands or save user preferences.

## Content-specific exceptions

- Tables, object lists, trees, charts, documents, multiline values and structured DLMS values may fill the available width. In mixed screens, ordinary scalar rows stay bounded while data areas expand. A value changing from scalar to structured must lift its scalar cap.
- Compact address, range, date/time, identifier, radio and repeated tariff groups retain widths appropriate to their content. Their containing property region stays bounded; related controls stay together.
- Profile Generic keeps paired metadata/read-range columns on the same responsive width budget, capped at 800 logical pixels. Sort mode and Sort object share the third metadata row; the reference matches the Period/Entries field width and retains selectable wrapping text. Its viewport grows to 120 logical pixels, with native vertical scrolling for longer references and no horizontal bar. Reset and Capture retain their original method bindings in a vertical stack at the top right, 120 logical pixels wide, with 32-pixel buttons and an 8-pixel gap. Below a viewport width of 720 logical pixels, place the stack above the full-width metadata to keep both fields readable. Italy-specific whitelist actions stay in the bottom footer; Capture Objects keeps its existing column-action footer. Its numeric entry/count/day inputs use the same 32-pixel visible input height and 40-pixel rows as the metadata fields. Center date range pickers at native preferred height within those rows so their checkboxes stay compact. Stack Count and To beneath their paired fields in narrow editors, and keep the complete Read Entry caption visible. Preserve native spinner arrows, date checkboxes/calendar, formatting and read-mode bindings; center numeric text without increasing its font size or painting a second border. Activity Calendar keeps full-width profile lists beneath bounded property headers. Its outer and Active/Passive headers use the same padded `CompactRow` editors and aligned field rail; native profile tabs remain below those headers. Do not retain the legacy 20-pixel field height or apply anchored coordinates on top of the layout tables. Device Properties retains its deliberate two-column connection layout.
- IEC Twisted Pair shares remaining vertical space between its Primary addresses and TAB(i) lists, with a 96-logical-pixel minimum for each list. Reserve both action rows before growing the data areas. Keep native list scrolling for longer data, and outer scrolling when the entire editor cannot fit a short viewport.
- Image Transfer uses a compact 80-logical-pixel Images catalog row with native internal scrolling for longer catalogs. Blocks Status and the transfer log share the remaining height. Size no-scroll acceptance from the logical viewport and current DPI; retain reachable outer scrolling at genuinely smaller viewport heights.
- Dashboard cards/charts retain user-saved widths. The Add OBIS pane remains bounded by the dashboard sidebar; its fields share edges, with top labels normally and the existing 76-pixel label rail at short heights. Do not add an outer scrollbar.
- External Gurux media property panels keep their vendor-owned internal layout inside a bounded host. About/version information and document/list dialogs use their content-driven layout. Do not rewrite an external package to change its label rail.
- Every exception must be named in the screen coverage ledger with its reason. "Legacy designer width" is not a reason.

## Verification

Enumerate all compiled screens, not only the screens with recent screenshots. Render each affected screen and relevant tabs with empty, representative and long content. Include conditional sections such as image signatures, ciphering suites and signing modes. Check normal, narrow and restored-wide states; compare actual absolute input/caption bounds across related sections, including compound field-plus-action groups. A correct label column inside each individual table is insufficient. Check retained editor identity, binding/access state and forward keyboard order after reparenting. Compare typography with the baseline. Exercise available real monitor scales and minimize/maximize. Explicitly report unavailable physical monitor tests; synthetic scaling does not count as a real monitor round trip. Inspect captures as well as assertions. Use offline fixtures and temporary storage, preserving user meter files/preferences.

## Basis

Microsoft's [Windows layout guidance](https://learn.microsoft.com/en-us/windows/win32/uxguide/vis-layout) recommends capped form widths, consistent peer sizing/alignment and dimensions suited to expected content. [GOV.UK text input guidance](https://design-system.service.gov.uk/components/text-input/) likewise relates input width to expected content and available space. The 800/144/640 dimensions are this application's convention, chosen to match its existing compact editor style; they are not prescribed by those sources.

## Native button text height

Reserve the complete rendered text-line height as well as its width. Use the larger context-free/control-DC extent, then include the existing padding and native border/internal text insets. `Font.Height + 2` is not a sufficient native button height contract. Compact object buttons retain horizontal padding but add no redundant top/bottom padding; the native renderer already provides vertical insets. This preserves the standard 32-logical-pixel height at the tested body font while keeping the whole line visible. Larger fonts may require a larger measured minimum rather than clipped text or a reduced font.

The [vertical-caption followup](UI_BUTTON_TEXT_HEIGHT_FOLLOWUP.json) records a failing 9pt baseline on the 96-DPI display: a 32-pixel button with 6 pixels of padding and 10 native inset pixels leaves 16 pixels for a 20-pixel line. Zero extra vertical padding leaves 22 pixels, and both password captions fit with the same font and button size. 11 focused cases, 114 captures and 783 assertions pass at actual 96/120 DPI, including Clock/shared-style guards and Calendar/Association monitor/minimize/maximize gates. The named 9pt probe is test-only and does not claim the user main-window font state. Earlier width-only evidence remains historical.

Restore their height limits, actual heights and margins from the current DPI after parenting, handle, font, DPI and presentation changes have settled. Raise a stale maximum height before assigning the desired height. Metadata rows 0/1 retain the 40-pixel logical rhythm; the Sort object row keeps its independent adaptive height. Do not fill/stretch Sort mode to the height of a wrapped reference, replace bound controls, or scale a previous font/height value.
